# DataHarvester (Reaper) ネットワーク系テスト 動作確認

`@pytest.mark.network` が付与されたテストは netkeiba.com / JRA公式サイトへの実通信を
伴うため、オフラインの `python -m pytest -m "not network" -q` では実行されない。
本ドキュメントはこれらを手動実行するための手順とテスト内容のまとめ。

## 実行方法

```bash
# ネットワーク系テストのみ実行（詳細表示）
python -m pytest -m network -v

# ファイル単位で実行する場合
python -m pytest tests/test_jra_calendar_scraper.py -m network -v
python -m pytest tests/test_netkeiba_scraper.py -m network -v
python -m pytest tests/test_race_card_builder.py -m network -v
```

- 実行にはインターネット接続が必要（netkeiba.com / race.sp.netkeiba.com / JRA公式サイト）。
- `src/logic/scraping/common.py` の `scraping_header`（`User-Agent`付与）が無いと
  netkeiba.com からHTTP 400が返るため、ヘッダー付きでアクセスする実装になっている。

## テスト内容の要約

### tests/test_jra_calendar_scraper.py — JRA開催カレンダー取得

- **test_get_jra_calendar_has_calendar_columns**:
  `jra_calendar_scraper.get_jra_calendar(2025)` で2025年の開催カレンダーを取得し、
  `model.CALENDAR_COLUMNS` を満たし、かつ空でないことを確認する。
- **test_get_jra_calendar_matches_existing_2025_calendar**:
  スクレイピング結果と既存の `data/race_schedule/2025_race_calendar.csv` を比較する。
  以下4件の既知の差分（旧CSV側の誤りで、JRA公式に基づく新実装の値が正しい）を除き、
  完全一致することを確認する。
  - 京都(course=8) 1回: 旧CSVの (2/8→days=3, 2/9→days=4) に対し、新実装は (2/9→days=3, 2/10→days=4)
  - 福島(course=3)・小倉(course=10) 2回: 旧CSVの 6/29(times=3) に対し、新実装は 6/29(times=2)

### tests/test_netkeiba_scraper.py — レース結果・配当・出馬表のスクレイピング

確定済みの固定レース `FIXED_RACE_ID = "202405010101"`
（2024年1月27日 東京1回1日目1R）を使用し、既知の期待値と比較する。

- **test_scrape_race_results_returns_expected**:
  `scrape_race_results(race_id)` でレース結果テーブルを取得。
  shape `(16, 23)`、列構成、`index` が `[FIXED_RACE_ID]` のみ、
  1行目の `着順/馬番/馬名/タイム/単勝/course_len/race_type/horse_id/jockey_id` の値を確認。
- **test_scrape_day_race_result_returns_expected**:
  `scrape_day_race_result(race_id)` で日次レース結果テーブルを取得。
  shape `(16, 15)`、列構成、`index`、1行目の `着順/馬番/馬名/タイム/単勝/厩舎/馬体重` の値を確認。
- **test_scrape_race_returns_dataframe_matches_known_result**:
  `scrape_race_returns_dataframe([race_id])` で配当結果を取得し、
  `data/RaceReturns/05_tokyo/2024_race_returns.csv` から判明している確定値
  （単勝・複勝・枠連・馬連・ワイド・馬単・三連複・三連単、計12行）と一致することを確認。
- **test_scrape_race_card_returns_expected**:
  `scrape_race_card(race_id)` で出馬表ページを取得。
  レース情報(`info`/`race_info_df`)と `race_card_df`（shape `(16, 11)`、列構成、
  1行目の値）を確認。

### tests/test_race_card_builder.py — 出馬表生成（エンドツーエンド）

確定済みの固定レース `FIXED_RACE_ID = "202405010101"` を使用
（出走馬の過去成績・血統データはキャッシュ済み）。

- **test_make_race_card_returns_expected**:
  `race_card_builder.make_race_card(race_id)` で
  スクレイピング → 血統データ付与 → score/rank付与までの一連処理を実行。
  - `race_info_df` の値（race_type/course_len/weather/ground_state/class）
  - `race_card_df` の shape `(16, 16)` と列構成
  - 1行目の `馬名/horse_id/peds_0/peds_1/peds_4` の値
  - `rank` 列が 1〜16 の順列になっていること

### 既知の問題と修正（2026-06-18）

`src/logic/scraping/common.py` の `fetch_soup` が全ページをEUC-JP固定でデコードして
いたバグを発見・修正した。`race.netkeiba.com`（`scrape_race_card`/
`scrape_day_race_result`が参照）は実際にはUTF-8で配信されており、固定デコードだと
列名が文字化けして`KeyError`になる（`db.netkeiba.com`はEUC-JPのため、今まで
気づかれていなかった）。`response.apparent_encoding`による自動検出に修正済み。
このバグはおそらくnetkeiba.com側のエンコーディング変更（EUC-JP→UTF-8）が
本日中に発生したことで表面化したもので、ver3.0側の従来の実装が誤っていたわけではない
（このセッションの前半では同じ固定デコードで正常に取得できていた）。

なお `netkeiba_scraper.py` 内の `pd.read_html(str(...))`（リテラルHTML直接渡し）に対する
pandasの `FutureWarning`、および列drop時の `PerformanceWarning` が出るが、
いずれも既存実装の警告であり、現時点では動作・結果には影響しない。
